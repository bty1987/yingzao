## 八、教训沉淀(五跑迭代,三处产品真缺陷修复+一处脚本错)

1. **🔴 第二轮归因锚混用(产品缺陷)**:confirmByCustomer 把 **saleId** 传给 `decorations.queryOrderCustomer`(语义=装修单 id)→查 `decoration_order where id={saleId}` 永不命中→恒 300001。跨域契约的 id 语义锚(单据 id vs 装修单 id)在同名方法参数里最易混——修复=先取 sale.order_id 再查(用 loadSale 已取的行内列);
2. **🔴 双层消息解析(产品契约踩坑)**:`require(cond, code, key)` 第三参语义=**i18n key**(内部 msg(key) 再解析),我把 `msg("sales.notFound")` 已解析文案传入→NoSuchMessageException("销售单不存在")→110000「系统繁忙」。同文件 require/直接 throw 两风格并存时,新增代码先 grep require 签名;
3. **🔴 无 body 动作端点 415(产品健壮性)**:`@RequestBody` 端点收到无 Content-Type 的空 POST(冒烟 urllib data=None 习惯/任意客户端)→HttpMediaTypeNotSupportedException→110000。动作端点零 body 依赖时不声明 @RequestBody(与内核 begin/finish 同款);
4. **冒烟脚本错**:R21 段首次只挂了销售单→order_d,没重挂 order_d.customer_id→c_cid(R20 段已复位)→列表恒空——「双向挂接」才闭环;`urllib data=None` 的 POST 会变 GET(405→110000),动作调用必须带 `{}`;
5. **诊断法**:300MB 服务日志用 seek 尾段+按时间窗过滤(5 秒格点异常=keepalive 探针噪声,已知行为,勿误读);Bash heredoc(`<<EOF`)内 Java 文本块("""+\"转义)必炸——改 `<<'PYEOF'` 或 Edit 工具;改动后必须重打 fat jar 并核对服务进程启动时间(`mvn compile`≠jar 更新,第 82 次「运行中 jar 旧版」教训再应验)。
