## 一、做了什么

### 1. 内核审批发布侧迁总线(yingzao-core)

- `ApprovalService` 弃 `ApplicationEventPublisher` 改 `YzEventBus.publish`,三类事件带业务幂等锚点:eventKey=`approval-submitted-{id}` / `approval-finished-{id}`(一次审批唯一,事件天然幂等)/ `approval-transferred-{id}-{toUserId}`(**复合锚点**:同一审批多次转交各自成事件,转给不同人各自通知);
- 三个事件 record 的 javadoc 同步改口径(「事务提交后发布/监听」→「经内核事件总线发布/消费」)。

### 2. 内核通知自消费改 SPI(ApprovalNotifier → ApprovalNotifyConsumer)

- 原 `ApprovalNotifier`(内核自订阅三类审批事件发站内信,log.warn 吞异常)整文件 git rm,新建 `ApprovalNotifyConsumer implements YzEventConsumer`:通知失败不再丢,总线重试直至消费确认;
- **幂等查重守卫**(对齐 LeadAssignedConsumer 姿势):按 source_addon+source_type+source_id 查 yz_notification;submitted/finished 天然一单一次;transferred 锚点=`approvalId:toUserId`,同一审批重复转给同一人不重复通知;
- 审批是内核平台设施,三类均为内核自有事件,内核自消费不违反「内核不订阅业务事件」红线(RFC §6.7)。

### 3. 五插件监听器消费器化(各自 addon,原监听器 git rm)

| 消费器 | 回写链 | 原子性姿势 |
|---|---|---|
| `TerminationApprovalConsumer`(decoration) | 终止通过→合同线 3→6+联动作废 | `DecorationService.executeTermination` 自身 @Transactional |
| `LeaveApprovalConsumer`(example) | 多级派生 L2+业务终态回写 | 消费器方法 @Transactional(逻辑自含) |
| `TransferApprovalConsumer`(inventory) | 调拨通过双向过账/驳回置 3 | `ManifestService.executeTransfer` 自身 @Transactional |
| `RefundApprovalConsumer`(payment) | 退款执行/驳回零改动 | 消费器方法 @Transactional(逻辑自含) |
| `SalesRefundApprovalConsumer`(sales) | 退货单生效/预扣回加 | `SalesRefundService.onApprovalFinished` 自身 @Transactional |

- 统一口径:回写逻辑在 Service 的→消费器薄壳直调(Service @Transactional 在无外层事务时新建,语义等价旧 REQUIRES_NEW,军规 8 场景消失);逻辑在监听器自身的→消费器方法带 @Transactional;
- **异常语义分层(迁移红利具体化)**:BizException(守卫失配/状态已迁移,重放不会变好)→ catch + log.error 留痕归档;其他异常(DB 故障等基础设施失败)→ 上抛交总线退避重试——旧监听 catch Exception 全吞、故障也丢的时代结束;
- 重放安全逐一核验:decoration approval_id 守卫+条件 UPDATE/example approval_id 守卫(改挂后陈旧事件被拒)/inventory status 守卫/payment refund_approval_id+status 双守卫/sales 「重放守卫」注释明示——五链全部重放幂等,符合总线 at-least-once 契约;
- **全部依赖"会发事件的 Service"的消费器构造参数加 `@Lazy`**(对齐第 20 次先例):总线构造器收集全部消费者 ↔ 服务依赖总线,启动期环依赖 2 轮实锤(leadConverted→customerService→bus / refundApproval→bus 直环),@Lazy 断环后启动正常。

## 三、途中事故与根因记录(REQUIRES_NEW 修复尝试 → 锁互等 → 回滚)

1. **首轮冒烟 1153/1154**:唯一失败=「插件派生 L2 提交事件走总线」——pymysql 直查发现该事件**延迟数秒后由调度器消费确认(status=1)**,即嵌套发布的子事件 AFTER_COMMIT 同步回调不触发、出站箱留痕+调度器兜底全部正常(三件套设计起效,业务无损);
2. **根因定位(带观测日志实证)**:总线 AFTER_COMMIT 回调在发布方事务提交后执行,此时 Spring 线程上仍绑定该事务的"死上下文"(ConnectionHolder 未清理、同步集合未清空);消费器在其上以 REQUIRED 开事务被误判「加入已有事务」,实际既不提交也不触发 afterCommit——其内部 `bus.publish` 的子事件回调注册进死上下文的同步集合,**永不触发**;
3. **修复尝试(已回滚)**:dispatchTask 消费段包 `TransactionTemplate(REQUIRES_NEW)` 强制干净事务——L2 submitted 当轮归档问题解决(0.2s 级确认),**但实锤引发 yz_event_task 行锁互等**:双 dispatch 竞态(HTTP afterCommit 线程+调度器线程)下 markConsumed(REQUIRES_NEW 事务内持行锁未提交)与另一线程 claim(UPDATE 同行)互等,51 秒=innodb_lock_wait_timeout,POST /leaves 51.41s 实测;**评估为内核投递模型的深层并发改造(需 per-task 精确认领/投递互斥),非一夜可安全落地**,整体回滚;
4. **回滚后姿势(本批终态)**:主链事件同步投递不变;嵌套发布子事件由调度器秒级兜底(冒烟 2s 轮询参数下实测 <5s 确认);**冒烟对账步统一轮询等待**,消除断言 flake;修复排期挂起,见「下次执行建议」。
