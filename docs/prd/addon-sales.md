# PRD - addon-sales 主材销售

> 状态:草稿(2026-10-11,待业务确认)
> 老系统参考:sales 模块(实现者回溯指针见文末;实现口径见 `docs/rules/sales.md`,二者同日产出)

## 业务闭环(一句话)

门店导购为装修单开主材销售单,客户确认并收款后经出货、配送安装,与厂商完成结算,最终销售单完结——装修单的主材变现环节从开单到厂结收口;数据终态落在 `sales_order.status=5 完结` + `balance_status=3 已结算`(款项轴双 2)。

## 用户与场景

| 角色 | 场景 | 高频动作 |
|---|---|---|
| 门店导购/销售员 | 客户在门店选主材,挂装修单开单 | 开单(选商品/套餐)、改券改补、发客户确认 |
| 客户 | 微信侧确认单据与退货 | 单据确认(验证码+手机)、退货确认 |
| 财务/结算员 | 收款后按品牌与厂商结算 | 预结、厂结值修正、提交结算、驳回 |
| 厂商/供应商 | 对账(经 addon-supplier/门户视角) | 查看结算单、确认厂结值 |
| 仓配/售后 | 送货安装履约 | 生成配送项、四级推进、回传完成 |

## 核心流程(状态机文字版)

1. 开单(挂装修单,守卫=装修单存在且非废单)→ `status=0 初始`,套餐展开落明细,装修单账户状态联动;
2. 明细维护(仅 status=0 且未录款)→ 主单总额实时重算(**服务端算,不信任前端金额**);
3. 客户确认 → `is_affirm=1`(验证码+手机三重校验,服务端强制);
4. 收款(走 addon-payment,发布 PaymentCollected 事件)→ 款项轴 0→1→2;定金/补款确认联动生成按品牌预结算行(`balance_status 0→1`);
5. 出货挂单(addon-inventory,事件扣减计数)→ 配送项生成(守卫=已付款)→ 四级履约推进(配送→审核→确认→完结,各带操作留痕);
6. 厂商结算:预结 → 厂结值确认(服务端强校验厂结值>0)→ 结算(`balance_status 1→2→3`);驳回=删除预结行+主单回 0(**同单全部行原子处理**);
7. 退货:审批(approval)批准生成退货单 → 客户确认 → 生成退款款项+按 rid 幂等生成退货结算(负值行,守卫主单结算态,**不满足显式报错**);
8. 完结(守卫=全款确认+无未完配送项)→ `status=5`;废单(守卫=四轴全初始)→ `status=4`;
9. 跨域全部事件化:payment/approval/inventory 不直接写销售表,经 addons-api 事件由 addon-sales 自己回写。

## 闭环校验

- 闭环起点:装修单存在 → 开单成功;
- 闭环终点:完结(全款已确认+配送全部完结+结算 3 态)或 废单(仅初始态可达);
- 异常路径:退货(全退→status=2/倒单→status=3,审批驱动+金额负向结算);结算驳回(原子回滚到未结);金额校验失败拒绝保存;**客户确认/退货确认必须幂等**(重复提交拒绝不重建)。

## 非目标(本期不做)

- 外销线(oales):V2 精简版另立项(含 atttype 内购外购、收款即复核、部门奖励分成——均待拍板);
- 活动积分族(salesactivity 三兄弟):整体剥离会员营销插件,销售域仅留 `activity_id+amount` 绑定;
- 满意度问卷(salesprofile 三表):并入统一 survey 域(与客户满意度合并)V2;
- 批量收款 N:1、渠道支付适配、钱包:均属 addon-payment(其 PRD 已剥离);
- 满意度/金蝶凭证/薪酬关联:kingdee/salary 为商业插件只读消费;
- 品牌跳级权限与按配送批次分成克隆结算:【方林嫌疑】待拍板,默认 V1 砍(配送只做履约不驱动结算)。

## 验收标准

- [ ] 开单必须挂有效装修单;明细增删改后服务端重算总额,拒绝前端金额;
- [ ] 四轴状态机全部守卫落地:改单仅初始、全款确认后明细冻结、废单仅四轴初始、完结三条件;
- [ ] 收款事件驱动预结算行(按品牌 N 行),重复确认幂等;厂结值未填/为 0 服务端拒绝提交;
- [ ] 退货按 rid 幂等(重复发起拒绝),主单非结算态时显式报错而非静默;
- [ ] 结算驳回原子处理同单全部品牌行;
- [ ] 客户确认三重校验服务端强制(单传验证码或手机号均不放行);
- [ ] 金额统一最小单位(分)显式换算,件数/折扣倍率换算有文档;错误码 300000 段同码同消息;
- [ ] 库存/采购计数经事件流水,addon-inventory 不得直写销售明细表;
- [ ] i18n 中英双语;操作日志全覆盖(含状态重置类管理动作)。

## 实施注记(V2 定金款线,2026-10-18 第 65 次回写)

- **双线拆分**(V1102):开单/改单可约定 `deposit_amount`(厘,守卫 0≤deposit<total);录款(generateBill)时拆 `sales_deposit`(定金)+`sales_full`(尾款=总额-定金)两条款项单;deposit_amount=0 时单全款线,V1 行为完全不变;
- **双轴回归**:`deposit_status`/`fullpay_status`(-1 未录/0 已录/1 已付/2 已确认)对齐老 depositpayStatus/fullpayStatus 正统形态;收款/确认事件按 typeCode 分流(PaymentCollected/ConfirmedEvent 携 typeCode);
- **顺序门控复用字典基建**:sales_deposit sort 建议先于 sales_full(懒预置落 2/冒烟种子 2 vs 3),同组前置款未收即 270010——先定金后尾款,组织可经「款项类型」页自调;
- **定金确认即解锁结算**:任一线确认→按品牌预结算行(uk 幂等,先到先建)+结算轴 0→1;完结守卫=两线全确认(线未生成豁免);废单重置双轴;改单/明细冻结看双轴任一已付;
- **不迁**:退定金线单独退(老两路径不对称烂账,rules/sales.md §80,留 V2.1);定金行 onetype=3 单级结算行形态(营造以按品牌明细预结行统一承载,定金确认只推进资金与解锁,不另立单级行)。
